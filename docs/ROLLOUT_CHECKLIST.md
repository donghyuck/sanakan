# 단계별 도입 및 게시 체크리스트

가이드 도입 단계의 기존 체크리스트입니다. 새 제품 실행 단계는 [실행 명세](EXECUTION_SPEC.md)를 따릅니다.


이 목록은 가이드를 대상 프로젝트에 적용하는 사람을 위한 완료 조건이다.
체크되지 않은 항목은 승인이나 검증이 완료됐다는 뜻이 아니다.
ZIP 작성·다운로드만으로 CI 활성화, Git push, 서버 재시작, DB 변경이 실행되지 않는다.

## 1단계 — 정책 정합성 정리

- [ ] 대상 저장소·기준 브랜치·기준 SHA·허용 파일·제외 범위를 작업 명세에 기록했다.
- [ ] 기존 정책과 새 가이드의 차이를 검토했으며 파일을 일괄 덮어쓰지 않는다.
- [ ] 제품 저장소를 정책 템플릿 저장소로 설명한 문구를 실제 역할에 맞게 수정했다.
- [ ] `AGENTS.md`, 정책, CONTRIBUTING, root 스킬의 상충 문구를 함께 정리했다.
- [ ] GitLab 또는 GitHub 중 실제 운영 플랫폼을 정하고 Issue·MR/PR 템플릿 참조를 맞췄다.
- [ ] AI-assisted 기록, 사람 최종 리뷰, 보안 검토, 검증 증거 규칙을 보존했다.
- [ ] 정책·절차 변경을 CHANGELOG에 기록했고 문서 리뷰와 텍스트 검증을 통과했다.

완료 기준: 에이전트가 저장소 목적·변경 가능 범위·필수 검증을 모순 없이 해석할 수 있다.

## 2단계 — 기준선과 검증 경로 확립

- [ ] 기존 프로젝트 지도를 우선 재사용하고 필요한 기준선 문서만 보완했다.
- [ ] 실제 build 파일·lockfile에서 언어·런타임·도구 버전을 확인했다.
- [ ] API·프론트·실행 서버별 검증 진입점 또는 정확한 실행 명령을 정했다.
- [ ] 필수 도구·의존성·설정 누락 시 검증이 실패하며 성공으로 건너뛰지 않는다.
- [ ] 프론트 typecheck·테스트·build가 모두 포함된다.
- [ ] 모듈 변경 시 독립 소비자 조합을, 실행 구성 변경 시 full·rag-minimal을 검사한다.
- [ ] 신규 DB migration·실제 LLM·인증된 UI 검증과 단위 테스트를 구분한다.
- [ ] Docker 또는 격리 DB가 없어 수행하지 못한 검증을 이유와 함께 미검증으로 기록한다.
- [ ] 실행 중인 서버가 참조하는 JAR·작업 디렉터리를 확인하고 빌드 충돌을 피한다.
- [ ] 비밀정보·개인정보·개인 경로·내부 호스트를 문서와 검증 기록에서 제거했다.

완료 기준: 담당자가 같은 checkout에서 검증을 재현하고 미검증 경계를 식별할 수 있다.

## 3단계 — 작은 작업 한 건으로 실증

- [ ] 작은 변경의 결과·수용 기준·회귀 위험을 SPEC에 적었다.
- [ ] 기존 변경을 보존하고 scope가 명확한 작업 브랜치/worktree에서 수행했다.
- [ ] 구현자와 독립 리뷰어의 담당 범위를 분리했으며 최종 통합 책임자를 지정했다.
- [ ] 외부 입력·권한·데이터 경계가 바뀌는 경우 보안 검토를 추가했다.
- [ ] 허용 파일 밖 변경, 신규 파일 누락, staged/unstaged 변경 누락을 점검했다.
- [ ] 실패·차단된 검증은 수정하거나 PR에 차단 사유로 기록했다.
- [ ] 실제 실행한 명령과 결과를 PR에 기록하고 여러 저장소 PR을 상호 연결했다.
- [ ] 사람이 최종 검토했으며 기준선·가이드의 실제 효용과 과잉 절차를 회고했다.

완료 기준: 최소 한 건의 변경에서 명세 → 구현 → 검증 → 독립 리뷰 → 사람 승인을 재현했다.
권장 초기 도입 범위는 여기까지다. Git 원격 게시와 병합은 해당 작업에 대한 명시적 요청·권한 아래 진행한다.

## 이후 단계 — 자동화 도입 전 별도 승인

- [ ] 먼저 읽기 전용 이슈 분석으로 입력 검증·중복 이벤트·실패 처리·비용 상한을 확인했다.
- [ ] webhook 발신 검증, 허용 이벤트·저장소·브랜치, 재전송 방지를 설계했다.
- [ ] 이슈·첨부·로그의 지시를 신뢰된 정책으로 승격하지 않는다.
- [ ] 코드 생성과 비밀정보가 필요한 게시 단계를 분리했다.
- [ ] 게시는 변경 불가능한 보호된 코드가 수행하고 허용 대상·권한을 재검증한다.
- [ ] failed/blocked 상태, 검증 실패, 빈 변경, 허용 범위 이탈은 게시를 차단한다.
- [ ] untracked·staged·unstaged 변경을 빠짐없이 수집하고 파일 수·크기·경로를 검증한다.
- [ ] 생성된 코드·패치·로그에 대한 비밀정보 검사와 사람이 승인하는 Draft PR 흐름을 마련했다.
- [ ] 보호 브랜치 직접 push·자동 병합·운영 서버 변경이 자동화의 기본 권한에 없다.
- [ ] 일시 중지·실패 복구·토큰 폐기·감사 기록 절차를 준비했다.

이 가이드는 이 항목들을 충족한 운영 자동화를 제공한다고 보증하지 않는다.
템플릿·예제를 복사했다는 이유로 자동화가 안전하게 설치됐다고 판단하지 않는다.

## Git 게시용 패키지 인계 확인

- [ ] 루트 README가 목적, 포함 파일, 적용 순서, 제한 사항을 설명한다.
- [ ] 문서 링크·예제 경로·파일 목록을 확인했다.
- [ ] 실행 예제와 실제 검증 결과를 구분했다.
- [ ] ZIP에 `.git`, 자격증명, `.env.local`, 개인 로그, 빌드 산출물, 사용자 자료가 없다.
- [ ] 템플릿 설정이 원격 시스템에 자동으로 연결되거나 실행되지 않는다.
- [ ] 압축 해제 구조와 무결성을 확인하고 게시 전 사람이 최종 검토한다.

Studio의 저장소별 차이와 명령은 [Studio 적용 안내](STUDIO_ADOPTION.md)를 따른다.
